Code Architecture and Organization

How dependencies, modular systems, data boundaries, execution order, and implementation tradeoffs shape code that can change and grow.

Basic programming versus code organization

Payne Robinson describes programming as a broad label for what often becomes a code-organization problem. A developer can learn a conditional statement or function, understand an engine’s basics, produce “Hello, world,” or move a character on screen through documentation and tutorials. The greater difficulty begins when multiple working elements must interact and continue working as more content is added.

He illustrates the progression of organizational decisions with enemies and save data:

  • Should every enemy receive a separate script, or should one script hold the different parts of an enemy?
  • If those parts are reused across other enemies, where should the reusable parts be stored?
  • When those parts need to be saved, should their state go into an enemy-specific save script or a global save script?

The problem is not only making two things interact once, but making that interaction work for similar things added later. Robinson characterizes this as an abstract way of thinking and repeatedly seeks an organization that remains modular.

What established solutions can and cannot supply

Robinson says developers can find useful organizational solutions for platformers, roguelike deck builders, and other genres whose common structures have been worked out. Those solutions can be reused and combined.

No tutorial, however, has already organized the exact game another developer is making. Following one project’s structure too closely can also make the result behave like that project. An original mechanic may create organizational requirements the tutorial never had, requiring a new solution for the unfamiliar behavior while established patterns continue to support the familiar parts.

Recognize structural signs of spaghetti code

In professional software engineering, Jonas Tyroller defines spaghetti code as a codebase with a convoluted, tangled control structure that often lacks clean, modular design. Its execution paths become difficult to follow or maintain. He identifies four technical indicators:

  • Tight coupling: components are intertwined, so changing one area forces unintended changes in unrelated areas.
  • Lack of encapsulation: systems or logic modules are not isolated enough to be reused, tested, or replaced independently.
  • Unpredictable global state: information moves haphazardly instead of through controlled interfaces or defined data hubs.
  • Implicit dependencies: code relies on obscure side effects or unmanaged execution order, including behavior arising from default engine setups.

Tyroller describes code that grows without a formal architectural plan as a “big ball of mud.” The culminating problem is that the complexity of the connections between components exceeds the complexity of the features themselves.

Keep dependencies within the application hierarchy

The Shaggy Dev presents a non-exhaustive collection of practices for keeping code receptive to change. The foundational practice is to respect the hierarchy present in every application: dependencies should flow down the hierarchy rather than upward or laterally, and should generally reach only one level down. An object that depends only on its own area of responsibility can operate without assumptions about the application state and structure around it.

An isolated player can be placed in an ordinary level, a structurally different bonus mode, or an interactive level-selection menu. If it instead assumes that it always has a sibling named items, that the sibling directly contains coin objects, and that each coin exposes a particular sound-effect function, every location must reproduce that structure whether it needs it or not. Changes to those parent or sibling implementations can then break the player even though they are not part of the player’s responsibility.

Dependencies that reach too far downward create a similar problem. A player can ask an animation container to change an animation, but should not manipulate the individual frames or their bitmap data. If the implementation later changes from separate images to a sprite sheet, the player remains unaffected when it knows only how to request the high-level animation change.

Keep operating data with its logic

The Shaggy Dev generally recommends keeping data beside the logic that operates on it rather than retrieving an object’s data and changing it elsewhere. Generic utility functions may be an exception. In the animation example, the player should call a function on the animation container instead of accessing the container’s internal data and performing the transition itself.

This keeps animation behavior in animation-oriented code and limits unexpected external changes to its state. If an animation fails, the relevant logic remains in the container rather than an arbitrary function elsewhere in the application. The container can also expose one consistent interface to enemies, NPCs, and the player. The speaker cautions that this separation can erode when a developer makes what appears to be one small, exceptional change.

Separate immutable gameplay data from code

Tyroller separately recommends keeping immutable gameplay data, such as balancing values and text, outside executable code. He advises designing the game’s database early, ideally using spreadsheets or scriptable objects. The stated benefits are easier balancing and modding.

This recommendation concerns immutable gameplay data. The Shaggy Dev’s adjacent recommendation concerns keeping an object’s operating state with the logic that changes it.

Compose reusable behavior from components

Rather than building large monolithic objects or relying excessively on inheritance, The Shaggy Dev recommends composing complex objects from smaller, self-sufficient components. A player, several enemy types, and breakable crates may all need health behavior. A health component—or a broader stats component—can standardize and contain the required data and functions instead of making each object maintain a separate implementation.

Tyroller similarly recommends independent modules for behavior such as health or movement and explicitly proposes reusing them in future projects to save time. Components can make code easier to organize, test, replace, and reuse while avoiding inherited functionality that an object does not need.

Connect reusable modules with project-specific glue

Tyroller recommends connecting independent systems through dedicated, non-reusable glue scripts or in-engine events rather than direct references between the systems themselves. The isolated modules remain reusable while the glue is specific to one game.

Inject references needed at runtime

The Shaggy Dev defines dependency injection as supplying references to objects at runtime rather than compile time. It addresses cases in which an object still needs access outside its direct descendants. A state, for example, may sit below the object that owns it while needing to control that parent.

Hard-coding the parent reference would require a separate state machine for every object. Instead, the state can be written to control a compatible type, such as a rigid body, without referring to the eventual owner. At runtime, a parent passes the state a reference to itself. The state can then control that particular object while remaining reusable. In the source’s examples, composition and dependency injection can support generic movement, health, AI, and other behaviors across different objects.

Control execution order in complex projects

For complex projects, Tyroller recommends manually controlling the execution order of scripts rather than relying on an engine’s default order. The aim is to prevent unpredictable behavior and implicit dependencies created by unmanaged execution order.

Separate simulation from view

Tyroller recommends separating game logic—the simulation—from rendering and visuals—the view. The view should read from the simulation, reducing interdependencies between behavior and presentation.

Prioritize design patterns selectively

The Shaggy Dev recommends learning established solutions to recurring software problems rather than repeatedly creating replacements, while not treating every pattern as an advance prerequisite. Broader software-architecture study may be useful for developers pursuing systems-driven games. The speaker’s initial priorities are:

  1. State machines: the strongest recommendation, including for simple games, whether represented through what the transcript calls “enumerators” or through more object-oriented code.
  2. Observer: a close second whose support in many engines and programming languages can reduce the effort required to use it. The speaker describes it as a particularly high-return pattern to study.
  3. Mediator: a possible next subject when observer communication is too one-way. The source does not explain its implementation.

After becoming comfortable with a few patterns, a developer can research solutions to specific problems encountered in practice, read Game Programming Patterns, or explore a general software-engineering book for applicable material. This is the speaker’s suggested progression rather than an exhaustive or universal curriculum.

When experimental code becomes commercial code

Execute was not initially expected to become commercially viable, and Robinson says its code was poorly organized. Player requests after release appeared simple but were difficult to implement because the existing organization had painted him into a corner.

His specific example is a global script built around what he calls a “string-based dictionary.” The source does not specify its full implementation. Resources, save data, prestige, and interconnected machine behavior now make it costly to swap in apparently simple additions. Robinson knows how he could rewrite the structure but does not consider the required time worthwhile. In the prototype he was developing during the earlier conversation, he was instead spending substantial time establishing a modular foundation before that project grew.

One proposed redesign would have let players select a different machine each time they restarted a pit. Modularity alone would not have completed the feature: every machine would also need to be rebalanced against the linear chain of other machines. Robinson feared players would reject the linear design, but concluded from the released game’s reception that many primarily wanted to eliminate its population in approximately three hours and did not need all the proposed choices.

Functional code and deferred cost

Emerson describes himself as a “recovering software engineer” who deliberately accepts spaghetti-like code when stronger architecture would not improve the shipped player experience enough to justify its cost. Something can be good enough for the immediate project and may remain good enough forever. Robinson similarly argues that developers receive no player-facing credit for implementing a feature “100% better” when both versions work adequately.

The speakers also preserve the cost of that choice. Technical limitations in both games eventually required optimization, hard caps, or abandoned updates. More modular architecture might have made later work easier, but might also have delayed release without improving the game’s fun or sales. The source does not resolve that tradeoff into a universal preference for either clean architecture or rapid implementation.

When an engine-level solution is outside his interest or available time, Emerson often changes the design problem instead of altering the engine’s source. The resulting performance and implementation tradeoffs appear in Game Performance and Technical Constraints, while the broader relationship between “good enough” implementation and finishing appears in Project Scope, Risk, and Sustainable Development.

Improve architecture through practice

The Shaggy Dev likewise argues against spending weeks at the start of a project trying to perfect code before its requirements are known or even a small vertical slice exists. Trying to learn every design pattern immediately can replace practice with theory, cause burnout, and leave a developer without direct experience of why or how a pattern helps. In the speaker’s formulation, a game with mediocre code that ships is preferable to a perfectly coded game that never does.

One acceptable learning path is to work until a pain point appears and then research how to address it. On a small project, it may also be useful to implement something poorly, finish it, examine the resulting problems and lessons, and research a better approach for later work. The speaker presents code-style improvement as iterative because game development and software development are both career-scale disciplines that take time to learn. The wider role of small experiments and repeated attempts appears in Learning Game Development Through Constraints and Experiments.

Separate demo content from shared systems

Chris Zukowski recommends designing a Steam demo as a deliberately accelerated experience rather than exposing an unchanged opening from the full game. From a software perspective, he suggests separating code from content so the demo can swap or toggle its content, progression, and pacing without becoming an entirely independent game.

He acknowledges that this architectural separation is easier to recommend than implement. The advice identifies a desired capability rather than a prescribed code structure: shared systems should support a demo that removes slow setup, reaches representative play quickly, and can still benefit from fixes made to the full game. The player-facing reasons for that design appear in Steam Demos, Festivals, Launches, and Commercial Lifecycle.

Repeated versions as architectural learning

Robinson made Execute twice before producing the released third version. He built the first in the engine transcribed in the earlier source as “GDAU” and concluded that he lacked the skills to finish it. The second expanded into a world map, robot armies, a parasite, a lightning minigame, and a large skill tree of self-operating machines connected by assignable resources. He eventually found the interactions too difficult to organize and shelved it.

The released version returned to the smaller initial concept while retaining selected ideas. His other project, Grid Tweaker, had similarly passed through repeated Pico-8 versions. These iterations accompanied his willingness to preserve an idea while replacing an implementation that exceeded his current skills or organization. The progression consequences are covered in Progression, Rewards, and Player Agency.
